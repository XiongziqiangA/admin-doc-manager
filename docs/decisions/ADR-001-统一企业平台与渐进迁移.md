# ADR-001：采用统一企业平台与渐进迁移

## 状态

Accepted

## 日期

2026-09-11

## 背景

行政资料管理系统当前使用 React、NestJS、Prisma 和 PostgreSQL，承担文件、分类、版本、搜索、财务归集和项目事项管理。资产设备系统使用原生 JavaScript、Express 和 SQLite，已经实现资产台账、流转、盘点、维修、审批、文件知识库和 AI 辅助。

如果只把两个前端页面拼接在一起，系统仍会保留两套账号、权限、项目、附件和数据库。跨模块关联、统计、备份和权限校验将长期依赖同步逻辑，无法形成一个可靠的企业管理系统。

## 决策

1. 以行政资料管理系统为统一主平台。
2. 保留 React、Ant Design、NestJS、Prisma、PostgreSQL 和 Electron 技术栈。
3. 将资产系统业务按模块渐进迁移到 NestJS，不长期运行双后端。
4. 将资产 SQLite 数据迁移至 PostgreSQL，迁移验收后旧系统只读观察并退役。
5. 用户、部门、项目、文件、AI 配置和审计只保留一套主数据。
6. 资产项目映射为 `BusinessMatter(type=PROJECT)`，资产附件映射为统一 `Document`。
7. 当前只启用管理员和员工角色，但权限模型支持后续增加专业角色与数据范围。
8. 每个迁移阶段必须通过现有行政功能回归，未完成模块使用功能开关隐藏。

## 被否决的方案

### iframe 或导航拼接

实现快，但身份、权限和数据仍然分裂，不满足统一系统目标。

### 前端同时调用 NestJS 和 Express

会产生两套鉴权、错误格式、部署和审计，跨模块事务无法保证。

### PostgreSQL 与 SQLite 长期双写

双写失败后难以判断哪套数据正确，也会显著增加迁移和运维风险。

### 一次性重写全部资产系统

变更范围过大，难以定位回归问题，也无法保证现有行政系统持续可用。

## 后果

- 合并时间比页面拼接更长，但最终只有一套可维护系统。
- 需要建立可重复、可校验、可回滚的数据迁移工具。
- 资产系统旧仓库在迁移期作为行为参考和数据来源，不继续增加新业务功能。
- 合并期间使用独立分支和功能开关，每个纵向切片完成测试后单独提交。
- 完整方案见 `docs/企业管理系统完整合并方案.md`。
